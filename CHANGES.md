# DealFlow360 — Changes So Far

Tracks what's been implemented against the plan in
`~/.claude/plans/radiant-twirling-snail.md`. Updated as work progresses.

## Summary

Implemented the first slice of DealFlow360: **unified authentication for the two
top-level user types**. Internal staff (Sales Rep, Sales Manager, Finance, Admin, ...)
and Customers (portal users) now log in through a single `/auth/login` endpoint, get
routed to a different dashboard shell based on `user_type`, and are structurally
separated — customers hold no RBAC role or permissions at all. Nothing beyond auth and
a staff-facing Customers CRUD screen has been built yet (no catalog, quotations,
warehouses, billing, etc.).

## Data model

- **New table `customers`**: `id, name, email (unique), company, phone, tier
  (bronze|silver|gold), hashed_password, portal_enabled (default true), created_at,
  updated_at`. No `role_id` — customers are structurally incapable of holding
  permissions, unlike `User`.
- Migration: `backend/alembic/versions/6545d60c0b63_add_customers_table.py`
  (autogenerated, applied).

## Backend

| File | Change |
|---|---|
| `app/customers/models.py`, `schemas.py`, `router.py`, `__init__.py` | New module. Plain `CRUDBase`-backed CRUD at `/customers`, gated on `customers:read`/`customers:write`. Password write path mirrors `app/users/router.py`'s `_prepare_user_data` pattern. |
| `app/core/security.py` | `create_access_token` / `create_refresh_token` now take a `user_type: Literal["internal","customer"]` and embed it as a JWT claim. Added `INTERNAL`/`CUSTOMER` constants. Required because `users.id` and `customers.id` can collide — `sub` alone is ambiguous. |
| `app/core/deps.py` | Rewritten around a single `get_current_principal` dependency that decodes the token once and returns a tagged `Principal(user_type, user, customer)`. `CurrentUser` and new `CurrentCustomer` are derived from it — each raises **403** (not 401) if the token is valid but for the wrong side of the system. `require_permissions` unchanged. |
| `app/auth/router.py` | `POST /auth/login` unified: looks up the email in `User` first, then `Customer` (must have `portal_enabled=true`); only ever checks the password against whichever table matched. `/auth/refresh` reissues tokens carrying `user_type` forward. `GET /auth/me` returns a discriminated `{user_type, internal, customer}` shape. `POST /auth/register` unchanged (internal self-registration only — customers are staff-created, never self-registered). |
| `app/auth/schemas.py` | `TokenResponse` gained `user_type`. New `MeResponse` (discriminated union shape). |
| `app/api.py` | Mounted the customers router. |
| `backend/alembic/env.py` | Registered `app.customers.models` for autogenerate. |
| `app/db/seed.py` | Seeds a demo customer: `customer@example.com` / `customer12345`, Gold tier, portal enabled. |

## Verified

- `docker compose` stack rebuilt, migration applied, seed ran clean.
- `curl`-level checks against the live backend:
  - Admin and customer both log in via the same endpoint and get the correct `user_type`.
  - `/auth/me` returns the correct discriminated shape for each.
  - A customer token hitting an internal-only endpoint (`/users`) gets **403**, not a
    silent failure.
  - Flipping `portal_enabled` off invalidates an already-issued, still-unexpired
    customer access token on its very next request (no wait for expiry).
- `tsc --noEmit` passes clean across all changed frontend files.
- **Not yet verified:** an actual browser click-through of login → redirect → guard
  bounce (no browser automation available in this environment) — worth confirming
  manually before relying on it.
